# US-04.01 — Create SePay Payment (part 1)

This branch contains payment-attempt creation, QR URL generation, the existing 15-minute online expiry rule, and the approved Commerce → Payment handoff. It excludes webhook confirmation, COD collection, payment-exception listing and PaymentConfirmed delivery.

Import [the collection](StyleMind-Commerce-Payment-Handoff.postman_collection.json). It has eight requests covering checkout, QR recovery/replay, owner isolation, internal authentication and amount mismatch. Tokens and fixture IDs are deliberately empty. Use disposable development data only.

## Configuration and startup

Supply database credentials and JWT settings using your ignored local environment. Set the same random `STYLEMIND_COMMERCE_PAYMENT_TOKEN` in Commerce and Payment. Configure `STYLEMIND_SEPAY_QR_BANK_NAME`, `STYLEMIND_SEPAY_QR_ACCOUNT_NUMBER`, optional `STYLEMIND_SEPAY_QR_ACCOUNT_NAME`, and `STYLEMIND_SEPAY_PAYMENT_CODE_PREFIX` (default `SM`). Never commit actual credentials.

Commerce calls the fixed `STYLEMIND_PAYMENT_BASE_URL`; Compose supplies `http://payment-service:8083`. When running services directly, defaults are Commerce 8082 and Payment 8083. The Gateway exposes Commerce under `http://localhost:8080/commerce`; internal Payment endpoints are for service/operator access. Compose does not publish the Payment port.

After reviewing your local configuration, rebuild the two changed services in your own development environment:

```powershell
docker compose up -d --build commerce-service payment-service
```

This command is an operator instruction; it was not executed during this branch preparation. Payment Flyway V1 creates `payment_attempt`, `financial_transaction`, `payment_exception` and the pre-existing local `payment_outbox` foundation. V1 is copied byte-for-byte from the existing working implementation; it was not rewritten or split. No external database foreign keys exist. The latter tables have no settlement/dispatcher APIs in this part. Tests apply V1 only to disposable PostgreSQL.

## Supported order flow

1. Obtain a valid Customer JWT, an owned shipping address and an active cart through the existing Identity/Commerce APIs. Set collection `customerToken`, `shippingAddressId`, and `paymentMethod=SEPAY_VIETQR`. Supply another owner's JWT as `otherOwnerToken` for isolation checks.
2. Run checkout. Commerce commits the Order, then sends its own ID/customer/method/amount/state to `POST /internal/v1/payments/order-attempts`. The caller cannot supply an authoritative payment amount. If Payment is unavailable, the committed Order remains and checkout keeps its existing response.
3. Run `POST /api/v1/orders/{orderId}/payment-attempt` through Commerce to retrieve the QR result or recover from an uncertain handoff. Both Customer and Admin are restricted to their own Order. Missing and foreign Orders return the same 404.
4. Verify `amountVnd` and QR `amount` equal the accepted Order amount. The transfer content is the returned payment reference. The response is PENDING; no financial transaction or PAID Order transition is produced by creation.
5. Repeat recovery. The deterministic `initial-<orderId>` key returns the same attempt. Conflicting customer/amount/method is rejected. An initial online attempt expires at generated time plus 900 seconds; expiry is materialized when a creation request invokes stale-attempt cleanup, not by a background timer.

Internal collection requests require direct Payment access (`paymentInternalUrl`) and the configured service token. In Compose use an explicitly controlled development access method; do not publish internal ports automatically. Never use internal fixture requests against real customer Orders.

## Limits and pending decisions

- The older public `POST /api/v1/payments/attempts` contract remains in this branch, but calls `GET /internal/v1/orders/{orderId}/payment-snapshot`, which Commerce does not implement. Use Commerce checkout/recovery for the working integration. Public API unit/HTTP tests supply a controlled Commerce dependency; they do not prove that missing endpoint works at runtime.
- An expired initial attempt is replayed as EXPIRED under the same key. A policy and supported user flow for issuing a fresh QR after expiry remain **TBD**. This branch is an initial US-04.01 delivery, not a claim that every backlog condition is complete.
- QR integration constructs a `https://vietqr.app/img` URL. It makes no HTTP call to that provider. Missing bank configuration, upstream Payment failures/timeouts and lookup failures are tested locally; live provider/network/image errors are unverified.
- Pending COD attempt creation is retained as part of the previously approved handoff contract. No COD collection, webhook settlement, refund or confirmation delivery API is present.
- Delivery after Commerce crashes between commit and handoff is not guaranteed. No durable sender or automatic replay of uncertain handoff POSTs is introduced.
- No real bank transfer, live ngrok/SePay webhook, manual Postman run or persistent database migration was performed for this branch.
