# US-04.02 — Confirm Payment

Import [the collection](StyleMind-US-04.02-Confirm-Payment.postman_collection.json). These requests simulate SePay and must use disposable test Orders/data. Do not send fixtures to real customer/payment data. The collection itself has not been executed with Postman; automated HTTP/PostgreSQL and two-JAR tests are separate evidence.

## Setup

1. For the default HMAC simulator, keep `STYLEMIND_SEPAY_WEBHOOK_AUTH_MODE=hmac`, set `webhookAuthMode=hmac` and local `webhookSecret` to the matching value from `.env`. The collection signs `<unix-seconds>.<raw JSON>` using HMAC-SHA256 with `X-SePay-Timestamp` and `X-SePay-Signature: sha256=<hex>` headers; never export the secret. This exercises the implemented signature contract, not verified live-provider compatibility. Alternatively configure SePay webhook authentication as API key, with `STYLEMIND_SEPAY_WEBHOOK_AUTH_MODE=api-key` and `STYLEMIND_SEPAY_WEBHOOK_API_KEY` matching SePay's configured API key. This handler expects `Authorization: Apikey <key>`. Leave actual values only in ignored local environment variables. For API key simulation set `webhookAuthMode=api-key` and the local `sepayApiKey` variable.
2. Set the same new random `STYLEMIND_COMMERCE_SERVICE_TOKEN` in Payment and Commerce for the reverse PaymentConfirmed integration. This credential is separate from `STYLEMIND_COMMERCE_PAYMENT_TOKEN` used to create attempts. Do not reuse a customer's JWT or the SePay key.
3. Set `STYLEMIND_PAYMENT_EVENTS_ENABLED=true` in Payment; optionally set `STYLEMIND_PAYMENT_EVENTS_POLL_DELAY_MS` (default 10000). Compose now wires these references, but no ignored `.env` was modified for you.
4. Rebuild Commerce and Payment in your own development environment: `docker compose up -d --build commerce-service payment-service`. This is an operator instruction; it was not run during implementation. Commerce applies the new V7 inbox migration. Existing V1–V6 and Payment V1 were not changed. If a database already contains a different V7, resolve that migration history before deployment rather than editing an applied migration.
5. Enabling dispatch also sends older unpublished **SePay** outbox rows; invalid/terminal Orders are reconciled. COD collection and COD outbox delivery are outside this story. Dispatcher defaults to disabled until configured.

## Run fixtures

- Use Commerce checkout/recovery from the earlier handoff collection to create three owned SePay attempts. Fill `paymentReference`, `wrongAmountReference` and `latePaymentReference` from separate attempts. Fill `amountVnd` with the first Order's exact amount, `orderId`, and local Current Values for `sepayApiKey`, `customerToken`, `adminToken`. Exported credential defaults are empty.
- Run requests 1 and 2 in order. Request 1 creates a new provider event ID; request 2 reuses it. Expect one financial transaction and one outbox event, then one inbox receipt/history entry and Order PAID. Run request 9 after the polling delay. A webhook HTTP 200 acknowledges both settlement and exceptions, so HTTP status alone does not establish a successful payment.
- Requests 3 and 4 reject fractional money and a wrong credential without writing money. Request 5 sends amount 1 against a separate attempt whose expected amount must be greater than 1; it records AMOUNT_MISMATCH. Request 6 deliberately uses a synthetic future transfer timestamp to exercise LATE_PAYMENT against a separate attempt. These are simulation fixtures, not real SePay transaction records.
- Request 7 lists OPEN exceptions as Admin; request 8 proves a Customer cannot list them. The API supports bounded `limit` 1–100 and nonnegative `offset`; no secret fields are returned. Filter values use the existing reconciliation-status data; manual resolution is not implemented.
- Automatic delivery retries failed/unacknowledged events with the same event ID. Only a valid matching Commerce 200 receipt marks the row published. APPLIED changes only PENDING_PAYMENT to PAID; equivalent replay has no repeated effect. RECONCILIATION_REQUIRED preserves Order state and produces an ORDER_PAYMENT_REJECTED exception in Payment without undoing a real settlement.

When using ngrok on Gateway 8080, set `paymentUrl=https://<your-domain>/payment`. The SePay webhook URL is that base plus `/internal/v1/sepay/webhooks`. Keep the internal Payment-to-Commerce event endpoint on its configured service URL; it is not a bank webhook.

## Verification and limits

```powershell
mvn -o -B -ntp -f commerce-service/pom.xml '-Ddebug=false' '-DargLine=-Duser.timezone=UTC' verify
mvn -o -B -ntp -f payment-service/pom.xml '-Ddebug=false' '-DargLine=-Duser.timezone=UTC' verify
node scripts/validate-us0402-postman.cjs
# After regression succeeds; creates/stops only its own labelled database container and Java children:
node scripts/verify-us0402.cjs
```

The validator checks nine requests, fifteen JavaScript scripts and raw JSON templates; it does not execute HTTP or validate a remote JSON schema. The two-JAR script uses separate new service databases/logins, real service credentials, deliberately loses the first committed ACK, and checks durable retry plus cancelled-Order reconciliation. See [the implementation report](../docs/qa/US-04.02_CONFIRM_PAYMENT_REPORT.md) for actual results.

No persistent database, real bank transfer or SePay-originated/ngrok delivery was tested. The scheduler uses fixed-delay retries and rotating batches; there is no production dead-letter UI, persistent retry counter or backoff policy. Refunds, exception resolution, paid-order cancellation and new QR attempts after expiry remain outside scope/TBD. Local verification is not production readiness.
