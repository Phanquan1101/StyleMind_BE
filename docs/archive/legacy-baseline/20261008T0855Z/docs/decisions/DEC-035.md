# DEC-035 — Human-Approved V1 Architecture Infrastructure and Hybrid Integration Baseline

Status: HUMAN-APPROVED

Decision authority: Phan Đoàn Thế Quân — Solo Owner of StyleMind

Approval date: 2026-09-22

Decision source: Human approval titled `ARCHITECTURE CORRECTION — HUMAN APPROVED`.

## Decision

StyleMind V1 retains PostgreSQL, Redis, Apache Kafka, Qdrant, Neo4j and Docker Compose as approved architecture components. Each component has a distinct responsibility. The existence of the components does not by itself finalize bounded contexts, service names, database schemas, APIs, event schemas, provider choices or deployment beyond the approved local development baseline.

## Approved responsibilities and constraints

### PostgreSQL

- PostgreSQL is the authoritative transactional system of record for core business data.
- A microservice may own and mutate its own persistence boundary only.
- A service must not mutate another service's database directly.
- Exact service-to-data ownership and database schema remain later SAD/contract work; this decision does not assign a final service map.

### Redis

- Redis is approved only for ephemeral or distributed-support concerns, such as OTP TTL, rate limiting, cache, useful idempotency keys, short-lived stock reservation if later required, and payment/session expiry.
- Redis is not authoritative for Orders, Payments, Products, Inventory, Returns, Refunds or Wardrobe.
- Any use of Redis for a specific concern remains subject to the corresponding detailed specification and lifecycle rules.

### Apache Kafka

- Kafka is the approved asynchronous integration and event backbone.
- The communication model is hybrid:
  - synchronous REST for user-facing queries, immediate validation, commands requiring an immediate response and critical request/response coordination;
  - Kafka for domain/integration events, asynchronous side effects, cross-service state propagation, notification triggers and AI/catalog indexing.
- Events are created only when they represent a meaningful integration need. Kafka's presence is not a reason to create an event for every state change.
- Candidate event names in the approval are design inputs, not finalized event contracts. Exact payloads, versioning, delivery guarantees, ordering and retry semantics remain contract work.

### Transactional Outbox

- The preferred reliability pattern for database state plus Kafka publication is a transactional outbox.
- Unsafe database-plus-broker dual writes are not an accepted reliability baseline.
- Exact outbox schema, retention, relay behavior and operational evidence remain implementation/operational specification work.

### Qdrant

- Qdrant is approved as a vector retrieval/index layer for semantic Catalog retrieval, style similarity, embeddings and AI Stylist retrieval.
- Qdrant is not authoritative Catalog storage.
- A Product or Variant returned by Qdrant must resolve against authoritative Catalog data before it is displayed as purchasable or used in a purchase flow.

### Neo4j

- Neo4j is approved as a fashion relationship and knowledge-graph layer for relationships such as garment types, styles, colors, occasions, materials, silhouettes, coordination and compatibility.
- Neo4j is not the authoritative transactional Catalog.
- The approved graph role does not silently approve a complete fashion vocabulary, ontology, synchronization policy or AI knowledge policy.

### AI grounding pipeline

The approved high-level pipeline is:

`User Context + Wardrobe + Catalog filters + Qdrant semantic retrieval + Neo4j fashion relationships -> structured AI context -> LLM reasoning -> structured outfit candidate -> deterministic Catalog grounding -> validated outfit result`

- The LLM cannot invent authoritative Catalog Product or Variant data.
- Purchasable recommendations must be deterministically grounded in authoritative Catalog data, consistent with the approved AI and commerce baseline.
- Retrieval freshness, deletion, synchronization, provider/runtime, prompt, evaluation and failure behavior remain open specification work.

### Docker Compose

- Docker Compose is the approved local-development orchestration baseline.
- As implementation progresses, the local environment should include PostgreSQL, Redis, Kafka, Neo4j, Qdrant and the StyleMind services that exist at that point.
- Kubernetes is not introduced at this stage.
- This local baseline does not decide production hosting, cloud provider, deployment topology or operating targets.

## Candidate integration events

The approval names the following candidate events for later contract analysis: `ProductCreated`, `ProductUpdated`, `VariantUpdated`, `InventoryChanged`, `InventoryReserved`, `InventoryReleased`, `OrderCreated`, `OrderConfirmed`, `OrderCancelled`, `OrderCompleted`, `PaymentConfirmed`, `PaymentExpired`, `PaymentFailed`, `ReturnApproved`, `RefundRequested`, `RefundCompleted`, `WardrobeItemCreated` and `WardrobeItemUpdated`.

These names are not final contracts and do not imply that every event is required. Event selection must follow an explicit integration need and preserve existing business rules, ownership and idempotency requirements.

## Explicit non-decisions

DEC-035 does not decide:

- final bounded contexts, service names or service count;
- final database-per-service allocation or SQL schema;
- REST endpoints, request/response schemas or event payload schemas;
- Kafka topic names, partitioning, ordering, replay, retry or dead-letter policy;
- authentication, authorization, secrets, consent, retention or security controls;
- AI provider, model, prompt/runtime, latency, cost or evaluation thresholds;
- a carrier, bank, webhook or payout provider;
- production deployment, Kubernetes, cloud hosting or SLO/SLA targets;
- new product scope or any previously unresolved OPEN question.
