## Decision

The human owner approves the logical Domain Model and `docs/architecture/01_SAD.md` as the authoritative V1 architecture baseline and authorizes implementation preparation and implementation.

The agent may make reversible technical choices without another approval round when they do not change approved business behavior, V1 scope, money/refund semantics, payment semantics, user-visible security guarantees, AI functional promises or the approved major architecture direction.

## Approved implementation direction

- Java 21 and Spring Boot for backend services.
- React, TypeScript and Vite for the frontend.
- PostgreSQL for authoritative transactional business storage.
- Redis for ephemeral/cache/TTL/idempotency/support use cases only.
- Apache Kafka for asynchronous integration events.
- Qdrant for semantic/vector retrieval.
- Neo4j for fashion relationship/knowledge-graph support.
- Docker Compose for local development.
- Maven, Flyway, validation, consistent REST errors and versioned event contracts.

## Delivery authorization

The implementation sequence is authorized to begin with concise implementation-grade OpenAPI and event contracts, a security baseline, an AI implementation specification, a test strategy, a minimal agent harness, local infrastructure, compilable service scaffolds, the Catalog vertical slice, Catalog events/index foundation and then the Cart slice if the Catalog quality gates pass.

Technical decisions must remain reversible where practical, be recorded when material, and preserve traceability. No approved business decision may be reopened or silently changed.

## Technical boundary decision

For the initial repository implementation, the logical SAD slices are realized as these independently runnable applications:

| Application | Initial responsibility |
| --- | --- |
| identity-service | Identity, authentication foundation and customer access boundary |
| catalog-service | Authoritative Catalog and Inventory boundary |
| cart-service | Guest/User Cart and atomic merge boundary |
| checkout-service | Checkout, Order and post-purchase orchestration boundary |
| payment-service | Payment attempt/confirmation boundary |
| wardrobe-service | Smart Wardrobe boundary |
| stylist-service | AI Stylist orchestration, retrieval adapters and grounding boundary |

This is a reversible implementation mapping of the approved logical slices. It does not authorize direct cross-service database access. Notification, Administration and Audit remain explicit extension points until their first implementation slice is needed.

## Non-decisions preserved

This decision does not authorize changes to approved commerce behavior, provider selection, production deployment, enterprise IAM, advanced computer vision, real-time weather/packing, exact AI quality thresholds or any other unresolved business policy.

## Traceability

DEC-036 records the approval of the Domain Model and SAD and the delivery-mode change. It extends DEC-035; it does not supersede DEC-026 through DEC-035. Contracts, security, AI and test documents created under this authorization remain subordinate to the approved BRD, PRD, Domain Model and SAD.
