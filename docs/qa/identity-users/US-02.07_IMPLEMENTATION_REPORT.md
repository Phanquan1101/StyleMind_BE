## Implemented contract

All three routes require a valid access JWT with ROLE_ADMIN, and then verify that the JWT subject still exists, is ACTIVE, is verified, and still has ADMIN in the database. A stale ADMIN JWT is rejected from Manage Users after the actor loses eligibility.

| Method and path | Behavior |
|---|---|
| GET /api/v1/admin/users | AND-combined optional status, role and literal email substring filters; zero-based paging (default 20, maximum 100); stable registered_at DESC, account_id ASC ordering. A live-eligible actor is authorized under a shared transaction advisory lock; count, page and complete role sets come from one READ_COMMITTED SQL statement snapshot. Output contains only account ID, email, status, verification/registration timestamps and the complete sorted role set. |
| PATCH /api/v1/admin/users/{account_id}/status | Accepts only ACTIVE or SUSPENDED. Only ACTIVE ↔ SUSPENDED is allowed; reactivation requires existing email verification. Pending accounts cannot be activated here. |
| PUT /api/v1/admin/users/{account_id}/roles | Atomically replaces the nonempty role set with a unique subset of CUSTOMER and ADMIN. Both roles can coexist. |

No-op writes return success without data/session side effects. Actual self status/role changes are rejected. Suspending or removing ADMIN from the last qualifying Admin is rejected. Status and role changes do not revoke sessions; Login/Refresh use current state, while issued access JWT claims remain until expiry. No schema or migration was changed, and no Profile, Address, or other API gained a live-state gate.

The implementation keeps Controller → Service → Repository layering with Spring MVC and Spring JDBC. It uses only stylemind_identity; response DTOs do not expose password hashes or session/challenge data. All success and error responses on these routes use Cache-Control: no-store.

Administrative writes acquire the PostgreSQL transaction-scoped exclusive advisory lock (1397248846, 207) before locking actor/target account rows in ascending UUID order. The service rechecks actor and target state after locking, applies the guards, and performs the update or complete role replacement in one transaction. This serializes changes to the qualifying-Admin set across instances without adding schema. The list acquires the matching shared advisory lock before any actor/data read, then locks and checks the actor and reads the page. This makes a write that commits first visible to the GET authorization check while allowing a GET already authorized under the shared lock to finish before the write.

## User flows

1. **List:** Admin A filters/pages the list. The API checks A's JWT claim and live database eligibility, then returns safe, deduplicated account rows and complete roles without writing data.
2. **Suspend/reactivate:** Admin A changes target B between ACTIVE and SUSPENDED. Pending B cannot be activated. The transaction preserves verification time, profile, addresses, roles, password, challenges and sessions. Suspension blocks future Login/Refresh; existing access JWTs keep their baseline expiry behavior.
3. **Replace roles:** Admin A submits B's complete nonempty role set. The API serializes the write, rechecks A and B, enforces self/final-Admin guards, and replaces role rows atomically. Future Login/Refresh tokens use the new roles; existing JWTs are not rewritten.

## Live-authorization follow-up

The initial READ_COMMITTED/list-lock strategy was tested with true PostgreSQL lock contention before and after the fix. Before the fix, role removal allowed a stale Admin list request to return 200 and suspension produced 500. The corrected shared/exclusive advisory-lock protocol returns 403 when the Admin write commits first, lets an already-authorized GET finish when it acquires the shared lock first, and rejects that actor's next stale-JWT request. Count and page are read in one SQL statement snapshot. The detailed interleavings, status/code assertions, logs and database evidence are in [US-02.07_LIVE_AUTHORIZATION_FOLLOW_UP.md](US-02.07_LIVE_AUTHORIZATION_FOLLOW_UP.md).

Follow-up logs are retained, redacted and ignored by Git under `target/us0207-liveauth-20261010/`. The separate Postman smoke used a newly created Compose project and Mailpit; that project and its volume/network were removed afterward. No persistent database was used.
