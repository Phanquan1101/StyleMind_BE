## Finding and deterministic reproduction

**The finding reproduced against the unchanged implementation.** Tests used real embedded HTTP requests, PostgreSQL Testcontainers, signed test JWTs, latches, and observed PostgreSQL lock waits (`pg_stat_activity`, `wait_event_type='Lock'`, and `pg_blocking_pids(pid)>0`); they did not rely on simultaneous request start alone.

| Interleaving before the fix | Observed result |
|---|---|
| Admin B removes ADMIN from A and holds the write transaction; A starts GET with its old ADMIN JWT and is observed waiting on the account-row lock; B commits. | GET returned **200** and used the old repeatable-read authorization snapshot even though A's final database roles no longer included ADMIN. This was stale authorization, not an allowed already-authorized read. |
| Admin B suspends A and holds the write transaction; A's old-ADMIN GET is observed waiting; B commits. | GET returned **500** from a PostgreSQL repeatable-read serialization/lock failure instead of the contract's live authorization result. |

The saved pre-fix run intentionally fails its new expected-result assertions with the observed **200** and **500** outcomes. It is retained at [pre-fix-reproduction.log](../../../target/us0207-liveauth-20261010/pre-fix-reproduction.log); UUIDs and other identifiers were redacted.

### Root cause

GET used `REPEATABLE_READ`. Its authorization query established a transaction snapshot before `FOR SHARE` waited. Role removal changes `account_role` without updating the actor's `account` row, so after the competing writer committed the waiting transaction could still read the old ADMIN role from its snapshot. When suspension updated the locked account row, PostgreSQL instead rejected the stale repeatable-read transaction. Both outcomes violated the approved live-authorization contract.

## Fix and consistency rationale

- GET now uses transaction-local `READ_COMMITTED` and acquires the shared Manage Users transaction advisory lock `(1397248846, 207)` **before any actor or user-data read**.
- Admin status/role writes acquire the matching exclusive advisory lock before account-row locks. The lock order is advisory lock, then account rows (sorted UUID order for writes).
- After acquiring the shared lock, GET locks the actor row, reads current status/verification/roles, and authorizes. A write that committed before the lock is acquired is visible and can produce 403. A write arriving after GET passed live authorization waits until the read transaction completes; that already-authorized request may finish, and the next request with its stale JWT is denied.
- The list's filtered set, count, page, and complete role aggregation are one SQL statement. Under READ_COMMITTED they share one statement snapshot, so count and page remain consistent without a transaction-wide stale snapshot. This performs no database writes and adds no schema.

The approved authorization point and business rules did not change. There is no JWT-only fallback, global state gate, blacklist, retry-that-hides-errors, or schema workaround.
