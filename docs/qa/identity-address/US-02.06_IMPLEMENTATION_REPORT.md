## Implemented contract

The implementation uses Controller → Service → Repository with Spring MVC and Spring JDBC, and only the existing V1 `public.customer_address` and `public.account` tables. No migration, schema object, API Gateway, or other service was added or changed. V1–V3 remain byte-for-byte unchanged. Every owner operation derives its owner from JWT `sub`; `CUSTOMER` and `ADMIN` are both self-only. A write locks the owner account before reading/writing addresses and runs in one transaction. Exactly-one-default is maintained by this service's write path; it is not a database constraint, does not protect against direct SQL/other writers, and legacy anomalies are not silently repaired.

Implemented routes:

- `GET /api/v1/me/addresses`
- `POST /api/v1/me/addresses`
- `GET /api/v1/me/addresses/{address_id}`
- `PATCH /api/v1/me/addresses/{address_id}`
- `DELETE /api/v1/me/addresses/{address_id}`
- `PUT /api/v1/me/addresses/{address_id}/default`
- `GET /api/v1/locations/provinces`
- `GET /api/v1/locations/provinces/{province_code}/wards`

Example create request and response (phone and address are illustrative):

```http
POST /api/v1/me/addresses
Content-Type: application/json
Authorization: Bearer <access token>

{"label":"Nhà","recipient_name":"Nguyễn An","recipient_phone":"0912345678","address_line":"Số 1 đường Ví dụ","ward_code":"00004"}
```

```http
HTTP/1.1 201 Created
Location: /api/v1/me/addresses/4f8d5ae3-03bd-4d8a-a98d-7ce84edc0d10
Cache-Control: no-store

{"address_id":"4f8d5ae3-03bd-4d8a-a98d-7ce84edc0d10","label":"Nhà","recipient_name":"Nguyễn An","recipient_phone":"+84912345678","address_line":"Số 1 đường Ví dụ","ward_code":"00004","is_default":true}
```

Workflow mapping: CUSTOMER or ADMIN authenticates and the API gets owner identity from JWT `sub`; a missing owner is 404. List/detail/lookup are reads and do not create or repair state. Create validates/canonicalizes before the transaction, locks the account, re-reads addresses, checks the invariant, inserts and returns the generated resource. Patch locks first, reads the current row, merges only supplied fields and updates. Set-default locks and switches the two flags atomically. Delete checks the current owner set and either deletes the allowed target or returns the default-conflict response without mutation. Directory lookup uses the preloaded immutable projection and does not access customer rows. No checkout snapshot, Commerce request or Order side effect is implemented.

Request parsing distinguishes omitted, null and wrong JSON types; unknown/client-owned fields are rejected. PATCH is a merge after taking the owner lock. The first address is default; switching default is atomic; deleting a default with alternatives returns `409 DEFAULT_ADDRESS_CHANGE_REQUIRED`. Missing/foreign resources share 404. Address responses contain only approved Address fields and carry `Cache-Control: no-store`. Vietnamese phones are validated locally and stored as E.164. Directory lookup is local, immutable and has no network fallback.

The directory is a projection of `thanglequoc/vietnamese-provinces-database` v5.2.0, source commit `62b1abdfe39625289c37a58ef6678e9db3d37f84`; it contains 34 provinces and 3,321 wards. The loader fails startup on malformed metadata, mismatched counts, blank/duplicate values, invalid types or orphan wards. `libphonenumber` is pinned at 9.0.40.

Validation/security evidence is divided as follows: JSON shape, missing/null semantics, unknown/client-owned keys, Unicode/code-point limits, controls, UUIDs and phone lexical/region rules are unit-tested in `AddressRequestValidationTests`; metadata, counts, duplicates, blank/type/mapping corruption and leading-zero lookups are checked by `VietnamAdministrativeDirectoryTests`; authenticated role, owner, database and HTTP behavior is covered in `ManageAddressPostgresIntegrationTests`. All eight routes require the existing signed-JWT baseline and `CUSTOMER` or `ADMIN`; unsupported roles are 403 and absent/malformed/invalid tokens follow the existing 401 path. CUSTOMER and ADMIN both remain self-only. Foreign and absent resources are indistinguishable 404s. Address responses/errors do not include owner IDs, credentials, session values, raw request data or secrets; address responses are `no-store`.

Transaction and concurrency evidence: every write enters the separate Spring transactional persistence service (not a `this` self-call), locks `public.account` before re-reading address state and writes through parameterized, owner-scoped JDBC. The 9 PostgreSQL integration tests exercise list/read/create/patch/delete/default, all-route auth, A/B and ADMIN self-only ownership, account/legacy-invariant cases, rollback injected after write steps for create/patch/default-switch/delete, and five coordinated race classes: concurrent first creates, competing defaults, delete-default vs set-default, patch vs delete, and last-delete vs create. Tests assert the committed final database state and observed PostgreSQL lock coordination; Java `synchronized` and sleeps are not used as the correctness mechanism. No production failure hook was added.
