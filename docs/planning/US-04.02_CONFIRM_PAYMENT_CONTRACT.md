# US-04.02 — Confirm Payment

Owner authorization: explicit request on 2026-10-26 to complete all four supplied US-04.02 tasks. This reauthorizes the previously removed PaymentConfirmed integration for SePay only. It does not reintroduce SHIPPED-only COD collection or change US-04.03.

## Approved scope and implementation mapping

- Payment verifies its configured API-key/HMAC webhook credential before parsing. Preserve existing configured authentication modes; `none` remains an explicit development-only option, never a verified-provider guarantee.
- Reference must match an existing SEPAY_VIETQR attempt and the amount must be a positive whole JSON integer, without decimal/string coercion. Existing wrong-amount and late-payment exception behavior remains; no financial transaction is credited for either.
- Use the provider transaction time when supplied (Vietnam timezone); otherwise use receipt time as the existing contract does. An invalid supplied timestamp is rejected rather than silently changing the payment time. A transfer at or after expiry is late. Existing generated QR/public creation contracts are unchanged.
- Save an immutable financial transaction once, settle the attempt and write PaymentConfirmed in one Payment transaction. Serialize by attempt row and use existing unique constraints/provider identifiers. Duplicates must not create a second financial transaction, regress a settled attempt or leak a PostgreSQL aborted transaction.
- Send committed SePay outbox rows to the fixed Commerce `POST /internal/v1/payment-events` using a separate externally configured service credential. No caller JWT, Notification dependency or cross-service database access. Retry unacknowledged events with the same event ID after errors/timeouts/restarts; only a valid matching acknowledgement marks a row published. Outbound HTTP runs outside the local database transaction. Failed rows do not prevent later rows being attempted.
- Commerce adds only `V7__create_payment_event_inbox.sql`, the same previously approved and removed inbox scope. Remote UUIDs have no cross-service FK. Do not edit historical migrations. No Payment schema change is required.
- Commerce validates owner, method, exact amount and current Order state under a row lock. Only SEPAY_VIETQR/PENDING_PAYMENT transitions to PAID with one history entry. Missing, foreign, mismatched, cancelled or other terminal/inappropriate Orders are retained as reconciliation receipts; never reopen or regress an Order. Equivalent repeated payment events have no repeated effects. Same event ID with different content is a conflict.
- Durable outcomes are APPLIED, DUPLICATE and RECONCILIATION_REQUIRED. Acknowledging reconciliation stops transport retry but creates a Payment exception (provider COMMERCE) for the existing Admin list; settled money stays settled. This is bookkeeping, not a refund/manual resolution workflow.
- Preserve `GET /api/v1/admin/payment-exceptions` with Admin-only access, safe pagination/status validation and no secret fields. No new public Commerce/Admin receipt API is necessary.
- Dispatcher is opt-in with `STYLEMIND_PAYMENT_EVENTS_ENABLED=false` by default. Configuration/deployment is operator controlled; tests use synthetic credentials and disposable databases only. COD outbox rows remain outside this SePay-only dispatcher.

## Required evidence

Unit/HTTP/JDBC regression and isolated PostgreSQL coverage: credentials and malformed/fractional amounts; correct reference/exact amount; wrong amount, late and unmatched payments; sequential/concurrent provider duplicates; atomic ledger/outbox rollback; Admin versus Customer/missing JWT list access; event retry/lost acknowledgement/invalid acknowledgement; receiver content conflicts, replay, owner/method/amount mismatch and terminal Order protection. Provide an importable Postman collection and run guide. Structural validation is separate from HTTP execution.

Refunds, manual exception resolution, paid-order cancellation, fresh QR attempts after expiry and production credentials remain TBD/outside scope. No persistent migration or live bank transfer is authorized by local test execution.
