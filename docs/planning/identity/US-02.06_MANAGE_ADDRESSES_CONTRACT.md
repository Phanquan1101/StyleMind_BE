## 2. Schema and ownership boundary

Use only public.customer_address and public.account. Existing V1 columns map directly:

| API field | Database column |
|---|---|
| address_id | address_id (server-generated UUID) |
| JWT sub | account_id (never accepted from request data) |
| label | label |
| recipient_name | recipient_name |
| recipient_phone | recipient_phone (canonical E.164) |
| address_line | address_line |
| ward_code | ward_code (nullable string; leading zero preserved) |
| is_default | is_default |

V1, V2 and V3 are immutable. No migration, table, column, index, constraint, FK, province/ward database table, audit field, history, soft delete, or Commerce access is in scope.

There is no database-level unique-default constraint. The application serializes each Address write by locking the owning public.account row in the same transaction, checks the current owner state, then writes. This maintains the invariant for Address write paths in this service only. It is **not** a hard database constraint and does **not** protect against direct SQL or another writer outside the application. A detected pre-existing owner state with multiple defaults or addresses but no default is not repaired or backfilled; writes that cannot preserve the invariant fail safely and the anomaly is recorded without exposing address data.

There is no content deduplication or idempotency key. Two identical valid POST requests may create two addresses. POST is never automatically retried.

## 3. Actors and common rules

- All eight APIs require a valid JWT and ROLE_CUSTOMER or ROLE_ADMIN.
- Every /api/v1/me/addresses operation derives the owner only from JWT sub. CUSTOMER and ADMIN are self-only.
- A valid subject whose account row no longer exists returns 404 RESOURCE_NOT_FOUND.
- Missing and foreign addresses produce the same 404 RESOURCE_NOT_FOUND response.
- Province/ward lookup is account-independent but still requires the same JWT roles.
- Address PII responses carry Cache-Control: no-store.
- Address responses expose only address_id, label, recipient_name, recipient_phone, address_line, ward_code, and is_default. Nullable fields are included as JSON null. No owner ID, credentials, token, session or OTP is returned.
- Problem Details and correlation IDs follow existing Identity convention. Errors/logs do not include phone, address text, request body, SQL, stack trace, token, or secret.
- Explicit owner query parameters account_id, customer_id, or user_id are rejected with 400 INVALID_REQUEST; they never influence ownership.

## 4. API contract

### 4.1 Address response

    {
      "address_id": "<server UUID>",
      "label": null,
      "recipient_name": "Nguyễn An",
      "recipient_phone": "+84912345678",
      "address_line": "Số 1 đường Ví dụ, Hà Nội",
      "ward_code": "00004",
      "is_default": true
    }

### 4.2 GET /api/v1/me/addresses

- Actor: authenticated CUSTOMER or ADMIN; owner is JWT sub.
- Preconditions: subject account exists.
- Workflow: read only the subject’s addresses; do not create or repair rows.
- Response: 200 {"addresses": [...]}; an account with no rows receives {"addresses": []}.
- Ordering: is_default DESC, address_id ASC; this is stable, not a “newest” order.
- Postcondition: no database state changes.

### 4.3 GET /api/v1/me/addresses/{address_id}

- Actor/owner: as above. address_id must be a strict hyphenated UUID; malformed input is 400 INVALID_REQUEST.
- Workflow: query by both address ID and JWT owner.
- Response: 200 with one Address response.
- Missing address or address owned by another account: identical 404 RESOURCE_NOT_FOUND.

### 4.4 POST /api/v1/me/addresses

- Accepted JSON properties only: label, recipient_name, recipient_phone, address_line, ward_code.
- Owner and UUID are server-derived. is_default, owner/id fields, role/status and unknown properties are rejected.
- Validate and canonicalize before opening the write transaction where possible; then lock owner account, check current invariant and insert atomically.
- First successfully-created address is default; subsequent addresses are not default.
- Response: 201, Address response, and Location: /api/v1/me/addresses/{address_id}.
- Failure leaves no partial row.

### 4.5 PATCH /api/v1/me/addresses/{address_id}

- Body accepts the same five properties; unknown fields are invalid. {} is invalid.
- Omitted property retains stored value. label and ward_code may be explicitly null to clear. Explicit null for recipient_name, recipient_phone, or address_line is invalid.
- Validate a ward or phone only when that property is supplied. Merge against the latest row after acquiring the owner lock; never overwrite a stale pre-lock snapshot.
- Does not change is_default.
- Response: 200 with updated Address response. Missing/foreign ID is 404.
- Persistence failure rolls back the complete change.

### 4.6 PUT /api/v1/me/addresses/{address_id}/default

- Requires an empty/no-content request body. A non-empty body is invalid.
- Lock owner; check owner invariant and address ownership; unset old default and set target default within one transaction.
- Repeating the operation for the current default succeeds with 200.
- Response: 200 with the address that is now default. Missing/foreign ID is 404.

### 4.7 DELETE /api/v1/me/addresses/{address_id}

- Lock owner; check invariant and ownership before deletion.
- Non-default deletion is allowed. Deleting the only address is allowed and leaves an empty list.
- Deleting the default while another address exists returns 409 DEFAULT_ADDRESS_CHANGE_REQUIRED with no state change. The client must first set another address as default.
- No replacement is chosen implicitly. Missing/already-deleted/foreign ID is 404.
- Success is 204 with no body. No Commerce/Order data is read, cascaded, or changed.

### 4.8 GET /api/v1/locations/provinces

- Requires JWT and CUSTOMER/ADMIN; no user data access.
- Response: 200 {"dataset_version":"v5.2.0","provinces":[{"code":"01","name":"Thành phố Hà Nội"}]}.
- Province codes/names are strings; order is ascending code. Names use source FullName.

### 4.9 GET /api/v1/locations/provinces/{province_code}/wards

- Requires JWT and CUSTOMER/ADMIN; no user data access.
- Province code must be a known string from the pinned dataset. Unknown code returns 404 RESOURCE_NOT_FOUND.
- Response: 200 {"dataset_version":"v5.2.0","province_code":"01","wards":[{"code":"00004","name":"Phường Ba Đình"}]}.
- Ward codes/names are strings, preserve leading zero, are scoped to the requested province, and sort ascending code. Names use source FullName.

## 5. Validation contract

Address-specific parsing uses JSON tree values to distinguish omitted, explicit null, and wrong JSON types. It rejects non-object/null/malformed roots, unknown keys and number/boolean-to-string coercion without changing other API validation behavior.

| Field | POST | PATCH supplied value | Normalization and constraints |
|---|---|---|---|
| label | Optional; omitted/null stores null. | Omitted keeps; null clears. | String only; Unicode trim; 1–50 Unicode code points; blank/control rejected; no enum/uppercase. |
| recipient_name | Required non-null string. | Supplied value must be non-null. | Unicode trim; 1–100 code points; control rejected; other Unicode preserved. |
| address_line | Required non-null string. | Supplied value must be non-null. | Unicode trim; 1–500 code points; control rejected. User attests it is the full delivery address. No regex claims reality/deliverability; text is not appended with province/ward names. |
| recipient_phone | Required string. | Supplied value must be non-null. | Raw maximum 64 Unicode code points; outer Unicode trim; allow only ASCII digits, formatting whitespace, +, -, ., (, ); plus only once and at first position; parse with default region VN; valid-for-region VN (mobile or fixed); persist E.164. No line activation/ownership check and no network request. |
| ward_code | Optional; omitted/null stores null. | Omitted keeps; null clears. | String or null only; trim outer Unicode whitespace; nonblank exact code in pinned dataset. Preserve as string/leading zeros. No number coercion, padding, historical remap, or rewrite on upstream dataset change. |

PATCH must contain at least one accepted field. Any supplied non-null phone/ward is checked; unrelated patches do not revalidate old stored fields. Address text is a user-confirmed snapshot and is not enriched or silently remapped when the directory changes.

google libphonenumber is pinned to the stable Maven Central artifact com.googlecode.libphonenumber:libphonenumber:9.0.40 (Apache-2.0). The version is explicit; no range or dependency-wide upgrade is introduced.

## 6. Pinned administrative dataset

The source repository thanglequoc/vietnamese-provinces-database is not the Government/NSO itself; its README states that province/ward input comes from the National Statistics Office (NSO) administrative-category API and tracks government-issued effective dates. The current pinned release used for this task is v5.2.0, source commit 62b1abdfe39625289c37a58ef6678e9db3d37f84, tagged JSON source json/full_json_generated_data_vn_units.json. Its metadata is v5.2.0, 388/NQ-UBTVQH16, generated 2026-09-20T13:13:17Z.

This release reflects the effective 20 September 2026 Bắc Ninh changes; source metadata and the official decree register were checked. At transformation time the source validates as 34 provinces and 3,321 wards, with no duplicate codes, missing names/codes, or ward-to-province orphans. Projection retains only province Code + FullName, and ward Code + FullName + parent province code; GIS, English names, postal codes, SQL, history/crosswalk and generation scripts are excluded. The artifact is local immutable runtime data; there is no runtime HTTP fallback.

MIT license attribution and source/projection SHA-256 values are recorded beside the resource and in the implementation report. Dataset load is fail-fast on metadata mismatch, blank code/name, duplicate codes, invalid types, count mismatch, or missing/orphan province mapping. Lookup structures are immutable after one startup load.

## 7. Transaction and concurrency contract

All create, patch, set-default and delete operations execute through a Spring-proxied transaction. Each transaction locks public.account for the JWT owner first, then reads the current address set/state, checks the unique-default invariant, checks owner-scoped resource existence, writes, and reads any response before commit. Validation/directory lookups are local and occur before lock when possible; no network call is made inside the transaction.

Supported owner state is either zero addresses/zero defaults or one-or-more addresses/exactly one default. A legacy violation is neither corrected nor concealed by a successful write. Operations across different owners do not block on an address-level/global lock.

Concurrency outcomes must be equivalent to a serial order:

- Concurrent first creates may both succeed; exactly one of their rows is default.
- Concurrent set-default operations serialize; exactly one row is default.
- Default-delete vs set-default may conflict or succeed according to a serial order; final state has one default if any rows remain.
- Patch vs delete corresponds to a serial order; a patch cannot resurrect a deleted row.
- Delete-last vs create corresponds to a serial order; empty means zero defaults and non-empty means exactly one.

Tests assert final persisted state, not just HTTP statuses. Barriers/latches and observed PostgreSQL row-lock waits coordinate races; sleeps are not the sole synchronization evidence. Rollback tests compare all owner Address columns/state before and after injected test-only repository failures. No production failure endpoint is added.

## 8. Flow contracts

| Flow | Actor / trigger | Preconditions | System workflow and alternatives | Postconditions / API data |
|---|---|---|---|---|
| View list | CUSTOMER/ADMIN calls list. | JWT and owner account valid. | Select owner rows only; stable default/code ordering. An empty account receives an empty array. | No write; only the seven Address response fields. |
| View detail | CUSTOMER/ADMIN supplies strict address UUID. | JWT and owner account valid. | Owner-scoped lookup. Bad UUID is 400; absent/foreign resource is the same 404. | No write; one Address response. |
| Lookup province/ward | CUSTOMER/ADMIN selects a directory value. | Valid JWT/role and known pinned dataset. | Read immutable in-memory catalog. Unknown province is 404; no upstream fallback. | No database access; deterministic string-code result and dataset version. |
| Create | CUSTOMER/ADMIN submits recipient/address fields. | Required fields valid; optional ward known; phone valid VN; JWT subject account exists. | Canonicalize, start transaction, lock owner, verify invariant, insert. Empty owner gets first default; otherwise non-default. Duplicate content is allowed. | 201 + Location; exactly one default for non-empty owner. |
| Update | CUSTOMER/ADMIN patches own UUID. | Non-empty valid patch; owner exists; resource belongs to owner. | Validate supplied fields; inside lock read latest row; merge supplied values; preserve omitted/null semantics; update transactionally. | 200 updated Address; default unchanged; failed update leaves state unchanged. |
| Set default | CUSTOMER/ADMIN targets own UUID. | Owner invariant valid; target belongs to owner. | Lock owner, read current state, unset old and set target in same transaction. Repeating is successful. | 200 target with is_default=true; exactly one default. |
| Delete | CUSTOMER/ADMIN targets own UUID. | Owner exists; target belongs to owner. | Lock owner and state. Non-default/sole-address delete succeeds. Default with alternatives gets 409 without mutation. | 204; either no addresses or exactly one default. No Order/Commerce side effect. |

Checkout may later snapshot the selected address at a separately-approved Checkout boundary; this is a boundary note only and adds no implementation or cross-service behavior here.

## 9. Error and security mapping

| Condition | HTTP / code |
|---|---|
| Missing, malformed, invalid types, invalid field, unknown property/owner parameter, malformed UUID, non-empty default body | 400 INVALID_REQUEST |
| Missing/invalid/expired JWT | Existing 401 Problem Details contract |
| Missing CUSTOMER/ADMIN authority | Existing 403 Problem Details contract |
| Subject account absent; address missing/foreign | 404 RESOURCE_NOT_FOUND |
| Unknown province in pinned data | 404 RESOURCE_NOT_FOUND |
| Delete default with alternatives | 409 DEFAULT_ADDRESS_CHANGE_REQUIRED |
| Unsafe pre-existing default invariant or persistence failure | Generic infrastructure/internal error; never relabeled as validation/not-found; no repair |
| Unsupported method/content type | Existing 405 / 415 conventions |

Address route security matchers are method- and path-specific. Auth routes retain existing rules; no broad permitAll("/api/**") is introduced.

## 11. Out of scope and limitations

No frontend, admin access to another owner, map/geocoding/GPS, carrier/shipping fee, SMS/OTP for phone, contact ownership proof, email, address sharing, history/audit/soft delete, pagination/search, idempotency/outbox/event, Commerce/Order calls, cross-service FK, schema/migration, account-state policy, or US-02.07. A selected/validated ward_code establishes only that it appears in the pinned administrative reference data; it does not prove a street address is real or deliverable. Phone validation checks numbering-plan validity from the pinned library metadata, not assignment/activity/ownership.
