## 3. Contract proposal for the four endpoints

### Shared API and authorization behavior

- **CONFIRMED convention:** Identity routes use `/api/v1`; existing API errors use Spring `ProblemDetail` with `type`, `title`, `status`, `detail`, `instance`, `code`, `timestamp`, and optional `correlationId`. Do not define a new envelope.
- **OBSERVED security:** `SecurityConfiguration` allows only specific auth POSTs without JWT, then requires authentication for `/api/**`; the new paths currently fall through to that authenticated rule. The JWT decoder checks RS256 signature, expiry/issued-at, configured issuer/audience, and UUID `sub`/`jti`; known role claim values map to `ROLE_CUSTOMER` and `ROLE_ADMIN`.
- **PROPOSED — NOT APPROVED:** Add only exact GET/PATCH `/api/v1/me` and GET/PUT `/api/v1/me/style-profile` handling. Require an authenticated JWT with `ROLE_CUSTOMER` or `ROLE_ADMIN`. Both roles can operate only on their own `sub`; ADMIN gets no lookup/override privilege. Add method-specific matchers for these four methods ahead of the generic `/api/**` rule; do not permit them anonymously and do not change the other API matchers.
- Every operation parses the validated JWT subject as UUID and scopes SQL by that ID. No `account_id` in body, query or resource path can select an owner. A valid JWT whose subject account row no longer exists receives the proposed `404 RESOURCE_NOT_FOUND`; do not add a global DB account-state check or change the current stateless JWT behavior. Any new endpoint-specific existence lookup is limited to that request.
- Missing bearer: existing `401 AUTHENTICATION_REQUIRED`. Invalid/expired bearer: existing `401 INVALID_BEARER_TOKEN`, `WWW-Authenticate: Bearer`. A token with no recognized role should be denied with existing `403 ACCESS_DENIED` under the proposed role check.
- New response JSON follows the existing snake_case response convention (e.g. Register's `account_id`). Request DTOs explicitly bind snake_case field names and reject unknown fields locally; do not change global Jackson behavior. Field-validation/deserialization failures use existing `400 application/problem+json`, code `INVALID_REQUEST`.
- No endpoint calls Commerce, Notification, Stylist or another service. No email/JWT/session/account side effect is part of this story.

### 3.1 GET `/api/v1/me`

**PROPOSED — NOT APPROVED.** `200 OK`; read only `account.account_id`, `account.email`, and optional `user_profile.display_name` for the JWT subject. If the account exists but its optional `user_profile` row does not, return `profile: null`; do not synthesize `display_name`, create a row, or return 404. If the account row is gone, return 404 `RESOURCE_NOT_FOUND`. No writes.

Profile not yet created:

    {
      "account_id": "8b59c9e2-7fd0-4eba-9785-8fc6bbafe124",
      "email": "customer@example.test",
      "profile": null
    }

Profile exists:

    {
      "account_id": "8b59c9e2-7fd0-4eba-9785-8fc6bbafe124",
      "email": "customer@example.test",
      "profile": { "display_name": "Nguyễn An" }
    }

`account_status`, roles and auth fields are deliberately absent. Missing/invalid/expired JWT is handled before the controller as described above. A correctly formed subject UUID with no account row is not itself an authentication decoding error; the proposed route-local account lookup yields 404 without modifying global security.

### 3.2 PATCH `/api/v1/me`

**PROPOSED — NOT APPROVED.** Patch only `display_name`; this subresource has no other allowed property. `200 OK` returns the same shape as GET after update. Use PATCH as partial-update syntax, but because only one property is patchable, require exactly that property: omission, `{}`, explicit null, empty string and all-whitespace string are invalid (400 `INVALID_REQUEST`). A valid request creates `user_profile` on first use or updates it thereafter. Do not change Register to create a placeholder.

    { "display_name": "Nguyễn An" }

Reject unrecognized fields such as `email`, `account_id`, `role`, `account_status`, `password_hash` or `email_verified_at`; do not silently ignore them or mass-assign them. The proposed display-name normalization/length/Unicode policy is in section 5. Account must exist; otherwise 404 `RESOURCE_NOT_FOUND`. Writes touch only `user_profile.display_name`.

### 3.3 GET `/api/v1/me/style-profile`

**PROPOSED — NOT APPROVED.** `200 OK`, read only for JWT subject. When there is no `style_profile` parent row, return `{"style_profile": null}`; do not create a parent or child row. When present, return all five optional scalar columns and all three preference collections. Null scalar values remain JSON null; empty collections are `[]`. Return `style_codes`, `color_codes` and `brand_ids` in stable lexicographic order (UUIDs in canonical lowercase form). Stable order makes response and tests deterministic without making order meaningful in storage.

    {
      "style_profile": {
        "fit_preference": null,
        "height_cm": null,
        "usual_top_size": null,
        "usual_bottom_size": null,
        "shoe_size": null,
        "style_codes": [],
        "color_codes": [],
        "brand_ids": []
      }
    }

The example's all-empty object represents an existing parent row; absence is represented by null. No brand name or active flag is returned because Identity stores only the UUID reference and has no Commerce lookup contract.

### 3.4 PUT `/api/v1/me/style-profile`

**PROPOSED — NOT APPROVED.** Recommend conventional full replacement of the entire style-profile aggregate. All eight properties are required in the request so missing and explicit null can be distinguished:

    {
      "fit_preference": null,
      "height_cm": null,
      "usual_top_size": null,
      "usual_bottom_size": null,
      "shoe_size": null,
      "style_codes": [],
      "color_codes": [],
      "brand_ids": []
    }

Scalar null explicitly clears that nullable scalar. A missing scalar is invalid; a missing or null collection is invalid; an empty array clears that collection. Reject duplicate canonical codes/UUIDs rather than silently deduplicating. Reject unknown fields. The all-null/empty replacement creates the `style_profile` parent row, yielding an existing all-empty aggregate on the next GET. The `account_id` is always derived from JWT subject.

On success return `200 OK` with the same `style_profile` object shape as GET (not null), after the transaction completes. Invalid input returns 400 `INVALID_REQUEST`; nonexistent JWT subject account returns 404 `RESOURCE_NOT_FOUND`. Within one transaction, upsert the parent and replace the three child sets. Any failure rolls back the scalar and all collection changes. There is no cross-service call or other side effect.

### Proposed error/status summary

| Case | Proposed result | Basis |
|---|---|---|
| Valid GET/PATCH/PUT | `200`; JSON view for GET/PATCH/PUT | Proposed contract; follows current REST/DTO pattern. |
| Missing/invalid/expired JWT | `401` `AUTHENTICATION_REQUIRED` / `INVALID_BEARER_TOKEN` | Existing entry point. |
| Signed token without an allowed mapped role | `403 ACCESS_DENIED` | Existing access-denied handler, with proposed exact role matcher on the new routes only. |
| Subject account absent | `404 RESOURCE_NOT_FOUND` | Existing code/envelope convention; route-local behavior proposed. |
| Malformed JSON, missing required fields, wrong types, unknown fields, failed field validation | `400 INVALID_REQUEST` | Existing `ApiExceptionHandler`; endpoint-specific DTO strictness is proposed. |
| Unsupported method | `405 METHOD_NOT_ALLOWED` if Spring maps the path and method; otherwise existing routing behavior | Existing handler; not a new business error. |

All errors retain current Problem Details fields and correlation ID behavior. No new error envelope is proposed.

## 4. Validation: existing basis and concrete proposal

No finite values or ranges for fit/style/color/sizes/height/display name are present in the current backlog row, logical model, V1–V3, Identity README, current approvals or current source. V1 does not impose text lengths or numeric bounds. The referenced `OPEN-035/037/038/046` and `OPEN-051` remain open references, not approval. The proposal below is one implementable minimum contract, not a claim that product vocabulary has been decided.

### Recommendation for approval group B — NOT APPROVED

- **`display_name`:** trim leading/trailing Unicode whitespace; after trim require 1–100 Unicode code points; reject Unicode control characters; allow Unicode letters/marks, accents, internal whitespace and ordinary punctuation. Preserve the remaining submitted characters, including Vietnamese. Never generate a value from email.
- **`fit_preference`:** nullable; if non-null, trim, require a code matching `^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$`, then normalize to uppercase with `Locale.ROOT`. No finite enum is proposed because there is no approved vocabulary.
- **`style_codes` / `color_codes`:** each element must be a non-null code matching the same 1–64 ASCII identifier syntax, trimmed and normalized uppercase with `Locale.ROOT`. Reject blank/malformed items and duplicates after canonicalization. Permit at most 50 items per collection. This gives meaningful format/duplicate validation without inventing a set of styles or colors. No candidate enum values are supplied or implied.
- **`height_cm`:** nullable JSON number, interpreted in centimeters as supported by the column name; recommend range 50.0–250.0 inclusive and at most one fractional digit. Reject NaN/infinity, non-numeric JSON, out-of-range values and excess scale. The range and precision remain product decisions, not schema facts.
- **`usual_top_size`, `usual_bottom_size`, `shoe_size`:** nullable free-form labels; if non-null, trim, require 1–32 Unicode code points and reject control characters. Do not enforce a country/size-system enum absent owner input. Return canonical trimmed text.
- **Collection cardinality:** max 50 unique entries per style/color/brand collection. No DB constraint supplies a limit; this is proposed to bound request and row volume.
- **`brand_ids`:** require a canonical UUID string (case-insensitive hex accepted, hyphenated UUID form); bind as UUID. Reject malformed and duplicate IDs. UUID syntax validation is distinct from Commerce existence or `is_active` validation (section 6).
- **PUT structural validation:** exact known key set; require presence of all eight properties; scalars may be null; collections must be arrays and cannot be null. Do not change Jackson behavior globally to accomplish this.

Consequences if group B is not approved: implementation may validate JSON types, required fields, nonblank structural data and UUID syntax as dictated by already approved structure, but must not apply invented maximums/ranges, uppercase canonicalization or finite vocabularies as business rules. Backlog's “invalid preferences” cases need the accepted validation contract to have deterministic expected outcomes.

## 5. Security and data ownership

**CONFIRMED scope:** self-service routes only; no profile of another user and no administrative list/update API. **OBSERVED:** JWT `sub` is a validated UUID; known `roles` map to `ROLE_CUSTOMER`/`ROLE_ADMIN`. Existing `SecurityConfiguration` protects other `/api/**` paths with authentication and has exact public exceptions only for auth routes.

**Recommendation — NOT APPROVED (included in group A):** require mapped `ROLE_CUSTOMER` or `ROLE_ADMIN` for the four exact endpoint-method pairs. Both may use `/me` only for their own account from JWT `sub`; ADMIN has no subject override. This fits `/me` semantics and permits an admin to read/manage only the admin's own optional Identity profile. If owner wants CUSTOMER-only, deny ADMIN on these four routes only; do not infer it from role names.

- Never take owner identity from body/query; `/me` has no account ID path component.
- `?account_id=<another-user>` is never bound or used to select an owner; it must not alter the subject-scoped result. Body account IDs are unknown properties and are rejected. There is no cross-account path route.
- Reject attempts to write email, role, account status, account ID, password/hash, verification timestamp or any unrecognized property. Email/account ID, if returned, are read-only values from `account`.
- Do not return `password_hash`, role rows, challenge state/digests, refresh-session rows/digests or key material. Use explicit response DTOs, not persistence records.
- Do not add a current-account-status database check to the global JWT path. The proposed endpoint-specific account-row lookup exists only to return the profile and distinguish a deleted subject; it is not a new global revocation/state policy. Other APIs and already-issued JWT semantics remain unchanged.
- Existing correlation logging records request metadata, not body content. Profile endpoints must not log full request bodies or profile values.
- Customer A/B test: authenticated A request operates only on subject A; supplying B's identifier as an unknown field is rejected and never redirects the SQL owner. A cannot read/update B via query or path because no such selector exists.

## 6. Commerce brand-reference decision

**EXISTING SCHEMA/model:** `PROFILE_BRAND.brand_id` is a non-null UUID and part of `(account_id, brand_id)` PK. V1 comments say logical reference only and intentionally has no cross-database FK. The Commerce target model has `BRAND(brand_id UUID PK, name, slug UNIQUE, is_active BOOLEAN)` and `PRODUCT.brand_id` FK to it. Commerce has no business migration or current brand read API/controller, and no approved API contract exists for checking brand existence/active status.

Three distinct properties must not be conflated:

1. UUID is well-formed — Identity can validate locally.
2. Brand row exists — cannot be established by the UUID or Identity FK.
3. Brand is active/selectable — the target Commerce model has `is_active`, but Identity has no supported way to query its current value.

### Recommendation for approval group C — NOT APPROVED

For the current US-02.05 boundary, validate UUID syntax and uniqueness only, store the logical reference, and explicitly accept that an ID may be unknown or inactive. Do not query Commerce DB, add an FK, or add a Commerce endpoint. If the owner requires (2) or (3), defer only brand-reference verification/persistence until a separate Commerce-owned contract is approved; implement the independent `/me`, scalar style, style-code and color-code work without marking all of US-02.05 blocked. Unknown/inactive acceptance under the syntax-only recommendation must be visible in API docs and tests.

| Alternative | Effect |
|---|---|
| UUID syntax-only (recommended, NOT APPROVED) | Story remains within Identity and current schema; cannot guarantee existence/active. |
| Check through Commerce API | Requires a separately approved endpoint, response, active semantics, timeout/failure mapping and availability behavior; no such contract currently exists and creating the API is outside this story. |
| Defer brand portion | Avoids claiming invalid references are caught; backlog task 2 is only partially satisfied until the brand contract is resolved. Other profile work continues. |

The existing `OPEN-036` reference remains open. This memo's recommended syntax-only behavior does not close or reassign that ID.

## 7. Transaction and concurrency plan

**Observed convention:** Spring JDBC with `NamedParameterJdbcTemplate`; transactional service/persistence methods use Spring `@Transactional`; existing identity state-changing flows lock the account row before challenge/session rows. No profile locking code exists.

**Proposed implementation:**

1. Controller authenticates/validates request DTO and extracts only the JWT subject. Service owns profile rules, validation mapping, transaction orchestration and response composition. Repository owns parameterized SQL and ResultSet mapping. Keep the current Spring JDBC stack; no JPA, schema/migration, version column, or dependency is needed.
2. PATCH/PUT begin one database transaction, lock the owner row in `account` using `SELECT account_id ... FOR UPDATE`, and return the proposed account-not-found error if no row exists. Every profile write uses the same lock order: `account` first, then existing `style_profile` if separately locked, then child rows in fixed order `profile_style`, `profile_color`, `profile_brand`.
3. First PATCH upserts `user_profile` on `account_id`; first PUT upserts `style_profile`. The account row lock serializes first creation for that account across service instances without relying on an absent parent-row lock or adding a column. Use explicit `INSERT ... ON CONFLICT(account_id) DO UPDATE` for parent rows only after validation.
4. PUT updates the five scalar fields and fully replaces child sets (delete current rows then batch insert canonical requested values). All operations occur in the same transaction. SQL/constraint/insert failure rolls back parent/scalar and every collection change; never return a success DTO before commit succeeds.
5. Two first-time PATCHes serialize on the account lock; exactly one `user_profile` row remains, and the last lock holder's valid value is persisted. Two PUTs serialize the entire aggregate; final state equals one complete submitted request, never a mixture. No optimistic-lock guarantee is claimed because no version column exists. The selected behavior is serialized last-writer-wins.
6. GET operations are read-only and never lock for mutation. For style aggregate consistency, use a single PostgreSQL statement/snapshot or a short read-only `REPEATABLE_READ` transaction for parent plus collections; return stable sorted arrays. No transaction is held over a network call; this feature makes none.
7. Do not alter Register to write either profile row. Verify by regression that registration still creates no profile placeholder.

The account-row lock is also used by existing Identity Login/Refresh/Reset flows. A profile write may briefly serialize with one of those operations for the same account. Validate and normalize input before opening the transaction, perform no network calls under lock, and keep SQL limited to the profile rows to bound that contention. The recommendation does not hold a lock while doing password hashing or email delivery.

The business choice “last serialized PUT wins” is **PROPOSED — NOT APPROVED** as part of group A. The row-lock mechanism and service/repository organization are routine technical choices consistent with the harness, subject to approval of the specified concurrency result.

## 11. Phase A decision matrix — superseded by owner approval

The following matrix records what was unresolved when Phase A was written. Groups A/B/C are now approved as summarized at the top of this memo. Existing technical conventions—Controller → Service → Repository, Spring JDBC, Problem Details, exact JWT subject ownership and disposable PostgreSQL testing—remain the implementation approach.

### A. Response, lifecycle, access and PATCH/PUT/null semantics

- **Already supported:** exact four backlog routes and HTTP verbs in shorthand; Identity `/api/v1` convention; `USER_PROFILE`/`STYLE_PROFILE` rows are optional; `display_name` is non-null; style scalars are nullable; collections are keyed by owner+value; profile access must be self-owned; existing JWT/Problem Details security convention.
- **Approved:** `/api/v1` paths and all request/response/lifecycle, authorization, account-missing and concurrency semantics are specified in the owner-approval section above.

### B. Validation, vocabulary and ranges

- **Already supported:** schema allows nullable fit/height/size scalars; schema name `height_cm` identifies centimeters; text values are text with no length or check constraint; composite keys reject duplicate stored code per account. No current source defines accepted values/ranges.
- **Approved:** the owner selected the exact syntax-only rules and limits in the approval section. No finite style/color/fit vocabulary or size enum is part of this story.

### C. Brand-reference validation/dependency

- **Already supported:** V1 can store a UUID logical reference with owner-local FK only; Commerce target BRAND has `brand_id` and `is_active`; there is no cross-service FK and no current Commerce brand API/source contract.
- **Approved:** validate UUID syntax and duplicates only; store the logical reference without a Commerce call. Existence and active status remain deliberately unverified for US-02.05.
