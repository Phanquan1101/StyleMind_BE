## 3. API contract

All successful responses use application/json and Cache-Control: no-store. Error responses follow existing Problem Details and correlation conventions and also carry no-store for these routes. API caller identity is derived only from the validated JWT subject; no request property can select the actor.

### 3.1 GET /api/v1/admin/users

Query parameters:

- status: optional exact value ACTIVE, PENDING_VERIFICATION, or SUSPENDED.
- role: optional exact value CUSTOMER or ADMIN.
- email_contains: optional 1–254 code points after Unicode boundary trimming; case-insensitive literal substring. %, _, and backslash supplied by a caller are literal characters, not caller-controlled SQL wildcards.
- page: optional zero-based integer, default 0; no negative values or overflow.
- size: optional integer, default 20, range 1–100. Invalid values are rejected; they are not clamped.
- Filters combine with AND. Duplicate query keys, unknown keys, blank supplied filters, and malformed numbers are INVALID_REQUEST.

The sort is fixed: registered_at DESC, account_id ASC. Clients cannot select SQL columns or sort expressions.

Response shape:

    {
      "items": [
        {
          "account_id": "uuid",
          "email": "user@example.test",
          "account_status": "ACTIVE",
          "email_verified_at": "2026-10-09T12:00:00Z",
          "registered_at": "2026-10-01T12:00:00Z",
          "roles": ["ADMIN", "CUSTOMER"]
        }
      ],
      "page": 0,
      "size": 20,
      "total_elements": 1,
      "total_pages": 1
    }

Roles are a sorted, complete set. A role filter selects accounts using EXISTS semantics and does not truncate the returned role set. Each account occurs once. Items and count use identical filters in one SQL statement snapshot. There is no per-account network/query round trip. An account with no role rows (legacy/inconsistent data) is represented with an empty roles array and is not repaired by GET.

No password hash, session/token hash, OTP/reset challenge, profile/address data, internal authentication data, or secret is returned. No display_name/profile aggregate is returned.

### 3.2 PATCH /api/v1/admin/users/{account_id}/status

The path account_id must be a canonical 36-character hyphenated UUID; shortened or malformed forms are INVALID_REQUEST.

Request accepts exactly:

    {"account_status":"SUSPENDED"}

Supported requested values are exactly ACTIVE and SUSPENDED. Unknown properties, missing/null/blank/wrong-type status, PENDING_VERIFICATION, LOCKED, DELETED, BANNED, or other values are INVALID_REQUEST.

Success returns 200:

    {
      "account_id": "uuid",
      "account_status": "SUSPENDED",
      "email_verified_at": "2026-10-01T12:00:00Z"
    }

The returned verification timestamp is read-only. It is never changed by Manage Users.

Transition matrix:

| Current target state | Requested ACTIVE | Requested SUSPENDED |
|---|---|---|
| ACTIVE | 200 no-op; no data/session side effect | 200 if allowed; active-to-suspended |
| SUSPENDED | 200 if email_verified_at is non-null; suspended-to-active | 200 no-op; no data/session side effect |
| PENDING_VERIFICATION | 409 ACCOUNT_STATUS_TRANSITION_NOT_ALLOWED | 409 ACCOUNT_STATUS_TRANSITION_NOT_ALLOWED |
| Other/unrecognized legacy state | 409 ACCOUNT_STATUS_TRANSITION_NOT_ALLOWED | 409 ACCOUNT_STATUS_TRANSITION_NOT_ALLOWED |

Reactivation requires email_verified_at IS NOT NULL. A pending/unverified account cannot be activated or made login-eligible by an Admin. An anomalous verified/status combination is not repaired; only the approved transition is considered.

No-op means stored value already equals the requested supported value. It returns the current success representation without UPDATE, session action, timestamp change, or other side effect. No-op status/role requests by the authenticated Admin about their own account are permitted. A request that would actually change the caller’s own state is 409 ADMIN_SELF_CHANGE_FORBIDDEN.

Suspending a qualifying Admin is 409 LAST_QUALIFYING_ADMIN_REQUIRED if it would leave no other qualifying Admin.

### 3.3 PUT /api/v1/admin/users/{account_id}/roles

The path UUID uses the same strict format.

Request accepts exactly:

    {"roles":["CUSTOMER","ADMIN"]}

Roles are a nonempty set drawn exactly from CUSTOMER and ADMIN. Both roles may coexist. Input must be an array of strings; empty arrays, duplicates, unknown roles, case/whitespace variants, nulls, wrong JSON types, unknown properties, or an attempted actor/account owner field are INVALID_REQUEST. The service canonicalizes the set in lexical order for output and comparison.

Success returns 200:

    {"account_id":"uuid","roles":["ADMIN","CUSTOMER"]}

PUT replaces the complete set transactionally. Same-set requests are 200 no-ops with no row writes or session side effects. A real change to the caller’s own set is 409 ADMIN_SELF_CHANGE_FORBIDDEN. Removing ADMIN from a qualifying Admin is 409 LAST_QUALIFYING_ADMIN_REQUIRED when no other qualifying Admin would remain. The target’s account status and verification timestamp are unchanged.

## 4. Authorization and status/role rules

For each GET/PATCH/PUT, all conditions are required:

1. A valid baseline access JWT.
2. JWT contains ROLE_ADMIN (the Spring Security route matcher).
3. JWT sub parses as UUID and identifies an existing account row.
4. The current account row has account_status = ACTIVE.
5. email_verified_at IS NOT NULL.
6. Current account_role still contains ADMIN.

Failure of live actor conditions returns 403 ADMIN_ACCESS_DENIED, without returning user data or performing target mutation. Missing/invalid JWT remains 401; a valid JWT without ROLE_ADMIN is denied 403 by the security chain.

No live-state gate is added to Profile, Address, or another endpoint. A stale ADMIN access JWT that passes the claim matcher is rejected by the Manage Users service if the database actor no longer qualifies. The authorization point is transactionally defined in section 6; an already-running request is not promised cancellation.

Account transitions exposed by this API are limited to ACTIVE ↔ SUSPENDED. Register/verification remain the only approved route from PENDING_VERIFICATION to ACTIVE. SUSPENDED is not OTP lock. No role hierarchy or additional role is introduced.

Roles are a nonempty set. CUSTOMER and ADMIN may coexist. Register continues to assign CUSTOMER server-side. Public APIs do not accept a role.

## 6. Transaction, locking, and consistency

### 6.1 Administrative writes

Every status/role mutation uses a Spring-managed PostgreSQL transaction. An exclusive PostgreSQL transaction-scoped advisory lock serializes all Manage Users mutations across service instances. The reserved pair for this Identity database is pg_advisory_xact_lock(1397248846, 207). It requires no schema. The lock is held until commit/rollback.

Lock order:

1. Acquire the exclusive Manage Users mutation advisory lock.
2. Lock the existing actor and target public.account rows in ascending UUID order, deduplicated, using SELECT ... FOR UPDATE.
3. Re-read actor account status, verification timestamp and roles after the locks are held.
4. Read target status, verification timestamp and complete role set.
5. Check self-change, transition, and qualifying-Admin guards.
6. Perform the single status update or transactional full role replacement; check affected rows and re-read the resulting representation.
7. Commit.

The global transaction lock protects the qualifying-Admin membership set, including concurrent changes that would add/remove membership; a count-before-update outside the transaction is not used. Role deletion and insertion are one transaction. A failure rolls the entire set back.

All administrative mutations use the same exclusive advisory lock before account row locks. Existing Login, Refresh, Profile, Address and verification flows do not request this advisory lock. Manage Users waits for their account row locks when applicable, but those flows never subsequently request the Manage Users advisory lock, so the ordering creates no lock cycle. The procedure applies to this application’s approved writers. Operator provisioning must be done with the API/workload quiesced because direct SQL does not acquire this application lock.

A no-op obtains the mutation serialization and row locks to make its read/decision authoritative, but performs no data write, session mutation, or timestamp update.

### 6.2 Admin list and authorization

List uses a Spring-managed READ_COMMITTED transaction. Its first database operation acquires a shared transaction-scoped advisory lock using pg_advisory_xact_lock_shared(1397248846, 207). That lock statement may take a statement snapshot before waiting; the application does not use that snapshot to authorize or read user data. After the shared lock is acquired, a subsequent statement locks the actor account row FOR SHARE, and a subsequent fresh READ_COMMITTED statement reads the actor’s current roles. Admin writes acquire the exclusive advisory lock before their account-row locks. Thus, if a write commits first, the waiting list performs its live check against the post-commit state and denies an actor whose ADMIN role was removed or whose account was suspended. If the list acquires the shared lock first, a competing Admin write waits until the already-authorized list transaction completes. The authorization point is after the actor row and roles have both been read while the shared advisory lock is held. A request already past that point is not asynchronously cancelled.

Count, page rows, and complete role aggregation are returned by one parameterized SQL statement. Its filtered, paged, and total CTEs share that statement’s PostgreSQL snapshot; this preserves count/page consistency without REPEATABLE_READ. Role matching uses EXISTS semantics, does not truncate returned roles, and does not duplicate accounts. No write occurs during GET. The shared-advisory-before-row-lock order matches the write-side exclusive-advisory-before-row-lock order and prevents a lock-order cycle with Manage Users mutations.

### 6.3 Session consequences

Status/role changes never modify refresh_session. Login and Refresh continue to evaluate current database status/roles. A suspended account cannot Login or Refresh. Reactivation can permit an unexpired, unrevoked existing refresh session under current baseline rules. Newly issued tokens use current roles. Already-issued access JWT claims remain unchanged and valid through exp. A stale Admin JWT cannot call Manage Users after that actor loses eligibility because each Manage Users request performs the live check. Suspension does not promise immediate denial at Profile/Address or other APIs.

## 7. Three user flows

### A. Admin lists users

- **Actor/trigger:** An Admin opens the user list or submits filters/page in an admin client.
- **Preconditions:** Bearer token valid and claims ADMIN; actor’s live account is present, ACTIVE, verified, and still has ADMIN.
- **Steps:** Admin chooses optional exact status/role/email substring and page/size; calls GET. Filters are validated and ANDed; page is sorted by registered_at descending then account_id ascending.
- **Backend:** Start a READ_COMMITTED transaction, acquire the shared Manage Users advisory lock before any actor/data read, lock the actor row FOR SHARE, then read current status/verification/roles. Once authorized, obtain total, page and complete roles in one filtered SQL statement snapshot.
- **Alternatives/errors:** 401 for bad/missing JWT; 403 for missing claim or live eligibility; 400 for invalid/duplicate/unknown query; empty matching page returns items=[] and correct metadata.
- **Postcondition:** No database writes; response is safe, complete roles, no-store.
- **Unchanged:** Passwords, profiles, addresses, roles, statuses, challenges, sessions.
- **Auth effects:** No account token/session effects. A write that commits before the shared authorization lock is acquired is observed and can cause a 403. After the actor has been live-authorized while holding the shared lock, a competing Admin write waits and the already-authorized read may finish.

### B. Admin suspends/reactivates a target

- **Actor/trigger:** Eligible Admin A selects target B and requests SUSPENDED or ACTIVE.
- **Preconditions:** A meets all live Admin conditions. B exists. Only ACTIVE/SUSPENDED transitions are exposed; reactivation additionally requires verified email.
- **Backend:** Acquire advisory lock, lock A/B account rows in UUID order, revalidate A, reread B, apply no-op/self/transition/last-Admin rules, then update only account_status in one transaction.
- **Postconditions:** 200 response contains B’s ID/status/unchanged verification timestamp. Rejected changes leave database unchanged.
- **Unchanged:** B’s email/password/profile/addresses/roles/email_verified_at/challenges/refresh sessions.
- **Auth effects:** Suspended B cannot Login/Refresh. On reactivation, an existing unexpired/unrevoked refresh session can be used. An already-issued access JWT is not rewritten; it can continue to reach baseline Profile/Address APIs until exp. No global live gate is introduced.

### C. Admin replaces a target’s roles

- **Actor/trigger:** Eligible Admin A submits a complete role set for B.
- **Preconditions:** A is live-eligible; target exists; request contains a nonempty duplicate-free subset of CUSTOMER/ADMIN.
- **Backend:** Acquire advisory lock, lock A/B rows in UUID order, revalidate A, reread B roles/status, compare canonical sets, then enforce self and last-qualifying-Admin guard. Replace rows atomically.
- **Postconditions:** 200 response returns B and all sorted roles. A same-set request is a no-op.
- **Unchanged:** B’s account status, email verification timestamp, password, profile, addresses, challenges and refresh sessions.
- **Auth effects:** Future Login/Refresh tokens use the new role set. Existing JWT roles remain as issued. If B is an Admin whose role is removed, that stale Admin JWT cannot call Manage Users after its next request’s live actor check; baseline Profile/Address role claims remain as issued until JWT expiration.
