## Evidence from the current project

### Schema and model

- **OBSERVED:** Applied V1 defines public.account with account_id, email, password_hash, free-text account_status, nullable email_verified_at, and registered_at. It defines no enumerated account_status CHECK constraint. See identity-service/src/main/resources/db/migration/V1__create_identity_tables.sql:5-12.
- **OBSERVED:** public.account_role has (account_id, role_code) as its primary key and restricts role_code to CUSTOMER or ADMIN. Its key permits both rows for the same account; the database does not enforce one role per account. See V1__create_identity_tables.sql:14-19.
- **OBSERVED:** public.user_profile holds the current display name; public.refresh_session stores token_hash, issued_at, expires_at, and nullable revoked_at. It does not store a plaintext refresh token. See V1__create_identity_tables.sql:21-27,65-72.
- **OBSERVED:** No Manage Users repository methods, controller, service, or endpoint contract exists in current Identity source. AccountRepository currently reads an account by email/ID and its role rows; it has no paged/filterable admin listing or status/role administration method.
- **BOUNDARY:** Use only Identity-owned tables in stylemind_identity; no cross-service database access, new table, column, constraint, migration, or schema reinterpretation is in scope.

### Authentication and state behavior

- **CONFIRMED:** Register creates accounts in PENDING_VERIFICATION, assigns CUSTOMER server-side, and does not issue tokens. Successful email verification changes the account to ACTIVE and sets email_verified_at. See docs/governance/CURRENT_BUSINESS_RULES.md:9-11.
- **CONFIRMED:** Login issues tokens only when the password matches, status is ACTIVE, email_verified_at is non-null, and the account has at least one allowed database role. Other statuses are denied. See CURRENT_BUSINESS_RULES.md:25 and identity-service/src/main/java/com/stylemind/identity/service/LoginSessionService.java:43.
- **OBSERVED:** Refresh re-reads account status, verification time, and roles and rejects a non-ACTIVE account before rotating a session. See RefreshSessionTransactionService.java:42-62.
- **CONFIRMED / OBSERVED:** JWT roles are copied from account_role when issued and translated to ROLE_CUSTOMER / ROLE_ADMIN by the decoder. The resource server validates the JWT on each request; it does not query current account status or role membership for every already-issued token. See CURRENT_BUSINESS_RULES.md:27, JwtDecoderConfiguration.java:31-66, and SecurityConfiguration.java:40-56.
- **OBSERVED:** Current API security expressly protects profile/address routes for ROLE_CUSTOMER or ROLE_ADMIN; fallback /api/** requires authentication. No Manage Users route or /api/v1/admin/** role matcher currently exists. See SecurityConfiguration.java:40-56.
- **TBD:** If an admin changes a target’s status or roles, already-issued access JWTs retain their claims until expiration (currently 15 minutes). Refresh checks current database eligibility, but existing refresh sessions are not automatically revoked by a status/role update today. Whether Manage Users should add a revocation side effect is an owner decision; this memo does not change it.
- **OBSERVED, not a lifecycle approval:** Login tests use the string LOCKED as a fixture to establish that non-ACTIVE states are refused. That test does not define LOCKED as an approved account status or authorize an automatic lock/unlock feature.

## Proposed API contract for review

These paths and behaviors are implementation candidates only; none is approved by source existence or backlog wording.

### List users

GET /api/v1/admin/users?status={status}&role={role}&email_contains={text}&page=0&size=20&sort=registered_at,desc

- Authentication: valid access JWT and current actor authorization per the selected policy above.
- Pagination candidate: zero-based page, default size 20, maximum 100; deterministic order with account ID tie-breaker.
- Safe response candidate: items containing account_id, email, account_status, email_verified_at, registered_at, roles; optionally display_name; plus page, size, total_elements, total_pages.
- Repository reads account, roles, and optionally profile from the same Identity database. No password hash, refresh token hash, OTP/reset challenge, authorization data, or secret is returned.

### Update account status

PATCH /api/v1/admin/users/{account_id}/status

Request candidate: {"account_status":"SUSPENDED"}. Status name, allowed transitions, treatment of pending accounts, actor checks, response status, and session effects all require owner approval. No LOCKED lifecycle or automatic lock mechanism is inferred from tests.

### Replace account roles

PUT /api/v1/admin/users/{account_id}/roles

Set-valued request candidate: {"roles":["CUSTOMER"]}. Decide first whether multiple roles are a supported business state. Validate values against V1’s CUSTOMER / ADMIN constraint. Apply all approved guards in one transaction; do not permit client-side self-assignment.

## Transaction and concurrency proposal

**PROPOSED — NOT APPROVED:** list operations use a read-only transaction. A single status or role update runs in one Identity database transaction, revalidates the acting Admin if approved, locks the target account row, re-reads target status and role rows, checks approved transition/role guards, applies the update, and commits. If last-Admin protection is approved, serialize all Admin status/role-changing transactions using a single documented lock order (candidate: lock qualifying account rows in stable account_id order, then re-read roles/status before the write). A guard is meaningful only after the owner defines what counts as a qualifying Admin. No schema addition is needed for these candidates.

Any owner-approved refresh-session revocation should occur in that same transaction as the status/role change. Do not add it implicitly: it changes the session behavior and user-visible security guarantee.
